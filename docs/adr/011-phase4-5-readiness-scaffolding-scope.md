# ADR-011: Phase 4/5 readiness scaffolding — what's built vs. what's external

## Status
Accepted

## Context
The user asked to continue into PRD Phase 4 (supervised clinical pilot) and
Phase 5 (regulatory submission), building "all software, validation,
documentation, and regulatory-readiness components that can be done now,"
explicitly not stopping at "not attemptable." Three things in these phases
categorically cannot be done by a coding session, no matter how much
software or documentation exists around them:

1. **Real patient/subject enrollment and data collection** — needs an
   actual clinical site, actual patients or workers, and actual clinicians
   running actual sessions.
2. **Ethics/IRB approval** — needs a real ethics board reviewing a real,
   submitted protocol and making an independent judgment.
3. **Regulatory submission and clearance** — needs a real regulatory body
   (e.g. an MDA/FDA/notified-body equivalent) reviewing a real submission
   and making an independent judgment; no document this repository produces
   *is* that clearance.

Everything else in these phases — the software a pilot needs to run
safely and be monitored, the statistical tooling a study needs to plan its
size and analyze its results, and the documentation a regulatory dossier is
assembled from — is legitimately buildable now, and is what this pass
built.

## Decision

### Software (real, tested, live-verified — not stubs)

- **`adverse-event-record.schema.json` + `AdverseEventsModule`**
  (`services/backend-api/src/adverse-events/`): clinician-authored,
  regulatory-grade adverse event documentation (causality, seriousness,
  outcome, ethics-board reporting timestamp) — deliberately distinct from
  the existing real-time `SymptomReport`, which is a safety-FSM input that
  exists whether or not a study is running. See the schema's own doc
  comment for the full distinction.
- **`ResearchExportModule`** (`services/backend-api/src/research-export/`):
  operationalizes the `research_data_export` consent scope, which existed
  in `consent-record.schema.json` since Phase 0 but had no enforcement
  point until now. Exports de-identified session data (pseudonymous
  subject id, protocol metadata, the derived-event log) only when the
  subject's consent record has that scope active; structurally cannot leak
  raw video (the Event log it reads from never contains it) or the
  internal `consentRecordId` join key.
- **`PilotMetricsModule`** (`services/backend-api/src/pilot-metrics/`):
  real, computed aggregate metrics (quality-unsupported rate, cue/escalate
  rate, symptom-report rate, adverse-event rate) for a study's data
  safety/clinical oversight group (referenced but not built in
  `study-charter-skeleton.md`'s "Study C"). Every rate is `null`, never 0,
  when its denominator is 0 — the same never-fabricate-a-measurement
  principle as `quality_gate.py`, applied to study-monitoring statistics.
- **`app/analysis/technical_feasibility.py`** (ml-service): the exact
  primary measures `study-charter-skeleton.md`'s Study A names (absolute
  angle error median/95th percentile, Bland-Altman bias + limits of
  agreement, valid-sample rate) as real, tested functions plus a runnable
  CLI (`run_technical_feasibility.py`) — verified against synthetic paired
  data with a known injected bias, which the tool correctly recovered.
- **`app/analysis/sample_size.py`** (ml-service): sample-size/power
  calculators (Bland-Altman precision, proportion precision, a
  sensitivity/specificity-to-sessions translator) so the clinical lead can
  turn an assumed effect size into an enrollment target — the calculator
  does not choose the assumed effect size or desired precision itself;
  those stay TBD, same as `study-charter-skeleton.md` always said.
- **`apps/clinician-web`**: `AdverseEventsPage` (if built - see
  `docs/phase4/`), `PilotMetricsPage`, both read-only and reusing the
  existing clinician-only + audit-logged pattern from ADR-010.
- **SBOM generation** (`scripts/generate-sbom.sh`,
  `docs/regulatory/sbom/`): real CycloneDX SBOMs generated by real tooling
  for all three services, with an honestly-documented scoping caveat on
  the Python one (`docs/regulatory/sbom-process.md`) rather than a silently
  imprecise artifact.

### Documentation (drafts, checklists, and analyses — never approvals)

`docs/phase4/` (clinical pilot readiness) and `docs/regulatory/` (Phase 5
regulatory readiness) contain real, usable drafts: a clinical investigation
plan structure, a statistical analysis plan referencing the tooling above,
a safety monitoring plan, a data management plan, an informed-consent
template, a risk management file extending `hazard-analysis.md` toward ISO
14971 structure, an IEC 62304 software-lifecycle mapping, an IEC 62366
usability-engineering-file skeleton, a cybersecurity documentation set, a
verification & validation report citing this repository's actual test
counts, a device-classification analysis, and a labeling/IFU draft.

**Every one of these documents is explicit about what it is**: engineering
output prepared to hand to a clinical lead, biostatistician, ethics board,
or regulatory affairs professional — never a claim that those people have
reviewed, approved, or signed off on it. None of them are filed anywhere.
`docs/claims-and-scope.md`'s hard boundary applies to this new documentation
exactly as it applies to everything else in this repository: nothing here
claims clinical validation, regulatory clearance, or ethics approval has
occurred, because none of it has.

## Rationale
"Not attemptable" was true only for the three irreducibly-external actions
listed above. Conflating those with "therefore nothing in Phase 4/5 can be
built" would have left real, usable engineering and documentation work
undone. Building it now — to the same tested, live-verified, honestly-scoped
standard as every other phase in this repository — means a real clinical
lead and regulatory owner have actual tools and drafts to start from,
instead of an empty phase.

## Follow-up
- A biostatistician must review `docs/phase4/statistical-analysis-plan.md`
  and set the actual pass/fail thresholds `study-charter-skeleton.md` has
  always marked TBD; the tooling this ADR adds computes whatever numbers
  are asked of it but decides none of the thresholds itself.
- A clinical lead must complete `study-charter-skeleton.md` and
  `docs/phase4/clinical-investigation-plan.md`'s remaining TBD fields
  before any ethics submission is possible.
- A regulatory affairs professional must review
  `docs/regulatory/device-classification-analysis.md` and every other
  Phase 5 document before any real regulatory engagement — this repository
  reasons through the analysis but makes no jurisdictional determination.
- The `ml-service` SBOM scoping caveat (`docs/regulatory/sbom-process.md`)
  should be resolved by regenerating from an isolated environment or the
  built container image before submission.
